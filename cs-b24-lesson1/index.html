STEP 1 · QUESTION

Counting steps, not seconds

0 – 10 min · B2.4.1
  • Seconds depend on the computer; time complexity counts how the number of basic steps grows with the input size n.
  • Space complexity measures how the extra memory needed grows with n.
  • Big O describes the worst case growth and keeps only the dominant term: 3n² + 5n + 2 → O(n²).

STEP 2 · EXPLORE

Common complexities

10 – 25 min · B2.4.1
  • O(1) constant: same time whatever n (read arr[5], push onto a stack).
  • O(log n) logarithmic: halves the problem each step (binary search).
  • O(n) linear: one pass through the data (linear search, sum of a list).
  • O(n log n): efficient sorts (merge sort, typical quicksort).
  • O(n²) quadratic: a loop inside a loop over the data (bubble sort, selection sort).
✏️ Worked example: How 1 000 and 1 000 000 compare
  1. n = 1 000: O(log n) ≈ 10 steps; O(n) = 1 000; O(n²) = 1 000 000.
  2. n = 1 000 000: O(log n) ≈ 20; O(n) = 1 000 000; O(n²) = 10¹².
  3. Multiplying n by 1 000 multiplies O(n²) work by a million.
  4. Conclusion: O(n²) does not scale to big data.

STEP 3 · TEST

Calculating Big O from code

25 – 40 min · B2.4.1
  • Sequential parts add: O(n) + O(n) = O(n). Nested parts multiply: a loop of n inside a loop of n = O(n²).
  • A loop that runs a fixed number of times (10) is O(1).
  • Space: an algorithm that copies the list uses O(n) extra memory; one that sorts in place uses O(1).

STEP 4 · EXPLAIN

Scalability and choice

40 – 55 min · B2.4.1
  • For small n, a simple O(n²) algorithm may be fine and easier to write.
  • For large or growing n (millions of records, real-time systems), choose lower complexity, even if the code is harder.
  • Trade-offs: faster algorithms may need more memory (space) or sorted data.
